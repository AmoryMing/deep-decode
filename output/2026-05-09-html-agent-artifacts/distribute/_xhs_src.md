---
title: AI 不爱写 Markdown 了
---

## 护城河被自己拆了

Claude Code 团队成员公开说，他越来越不想让 Claude 输出 Markdown，而是直接生成 HTML 文件。Markdown 当年胜出，靠的是轻、好 diff、人愿意手改。但当"修改"这件事也交给 Agent，它最大的护城河就少了一半。人类留下的工作不再是逐行手改，而是判断方案是否可读、可比、可信、可操作。输出标准随之变了：从"我能不能方便改这个文件",变成"我能不能快速读懂它,并把决定喂回 Agent"。

## HTML 是工作台不是档案柜

别误读成"以后都用 HTML"。更稳的分层是：Markdown、YAML、JSON、代码仍是 source of truth，负责可追溯、可版本控制;HTML 是 rendered artifact,负责让人读懂、操作、分享。一个 PR 解说页可以用 HTML 渲染 diff、模块图、风险标签,但真正合并进仓库的还是代码 diff。配置编辑器能做表单和依赖警告,真正进系统的还是配置变更。HTML 的位置不是档案柜,而是工作台。

## 双向交互才是关键

原文最有价值的部分是 Two-way Interaction。不是只说 HTML 可读,而是让 Claude 做滑块、拖拽卡片、实时预览,再把人操作后的结果复制成 JSON、prompt、diff 贴回 Claude Code。例子很典型:把 30 个 Linear tickets 做成 Now/Next/Later/Cut 四列拖拽卡片;prompt 调参器左边编辑模板,右边用三个样例实时渲染,顺带显示字符数和 token 数。这不是文档,是一个短命但够用的操作界面,把人类判断变成结构化反馈。

## 一次性脚手架

这些界面做成正式产品会显得过度设计,写成 Markdown 又很难操作。HTML artifact 卡在中间:它是一次性的,但足够可用;不是产品,却能把人拉回循环。这意味着 Agent 的 UI 不一定是大产品里的固定界面,很多会变成任务现场临时生成的"脚手架"。用完之后,它的价值不是长期存在,而是把人从一大段抽象文本里拉回判断现场,做完就丢。

## 为什么是 Claude Code

不是普通聊天窗口,而是 Claude Code 更适合生成这类页面。原因不是模型本身,而是上下文入口。它能读文件系统、代码目录、Git 历史,也能通过 MCP 接 Slack、Linear、浏览器上下文。它不是凭空写一个漂亮页面,而是从真实工作材料里抽出结构再渲染。所以这篇真正押注的不是 HTML,而是"上下文充分的 Agent 可以为每个任务生成专用界面",HTML 只是当前最通用、浏览器原生支持最好的载体。

## 工程账并不轻

原文没回避缺点:HTML 可能比 Markdown 多花 2-4 倍时间,diff 噪声大,也比 Markdown 难 review。这足够让"HTML 替代 Markdown"刹车。文件要长期维护、多人协作、进仓库、接受审查时,Markdown 仍有明显优势——可读、可 diff、可合并。HTML 一旦夹进大量 inline style、绝对定位和脚本,人的审查成本会上升:页面看起来更清楚,源文件反而更不清楚。

## 三层分离才落地

企业落地更合理的是三层分离。第一层 source of truth:用 Markdown、YAML、JSON、代码保存可追溯事实。第二层 rendered interface:用 HTML 把复杂信息变成可读、可点、可比较的界面。第三层 audit trail:把人在界面里的操作导出成 diff、JSON、prompt 或决策记录,再进系统。这比"以后不用 Markdown"无聊,但更接近真实工作:两者分工,Agent 才不会在漂亮和可控之间二选一。

## 对从业者意味着什么

别只写"输出 Markdown",要定义 artifact 的用途:谁读、读完做什么、需要哪些交互、导出成什么。交付物分 source 和 view,不让 HTML 承担所有责任。同时要警惕:HTML 页面看起来更像成品,容易让人降低警惕,事实、引用、参数变更仍要回到可验证源。界面提升阅读率,不等于提升真实性。好的 Agent 输出格式,不是让人更少参与,而是让人更容易参与。
