嗨，欢迎来到 AI 前沿拆解。这一期讲一个看起来很小，但其实会影响 Agent 工作流的问题：Claude Code 到底应该输出 Markdown，还是直接输出 HTML？

这件事来自 Claude Code 团队的 Thariq。他写了一篇 X Article，标题叫《Using Claude Code: The Unreasonable Effectiveness of HTML》。中文圈 Berryxia 把它转述成“Markdown 失宠，HTML 的好日子要来了”。

这个说法很适合传播，但真正要拆的不是“HTML 终于翻身”，而是 Agent 输出的角色变了。

过去，AI 输出一段文本，人类打开、修改、复制、归档。Markdown 在这里很强，因为它轻、好读、好 diff、好手改。但现在，Agent 输出越来越像 spec、PR 解说、研究报告、设计方案、配置编辑器、prompt 调参面板。人类不再总是逐字修改，而是在读、比较、调参、审阅，再把结果喂回 Agent。

所以问题变成了：输出格式到底是为了方便人类手改，还是为了让人类继续留在 Agent loop 里？

Thariq 原文里最关键的一句话是，他越来越少直接编辑这些文件，而是把它们当作 spec、参考文件、头脑风暴输出。

这句话很重要。Markdown 最大的优势，是人类容易编辑。但如果编辑这件事也交给 Claude Code，Markdown 的护城河就少了一半。人类留下来的工作，不是手改每一行，而是判断这个方案是否可读、可比、可信、可操作。

这就是 HTML 突然变得有价值的原因。HTML 不是因为更漂亮才赢，而是因为它天然就是界面。它可以放表格、CSS、SVG、代码高亮、JavaScript 交互、canvas、图片、绝对定位和移动端适配。Markdown 当然也能表达结构，但复杂到一定程度后，模型就会开始绕路，用 ASCII 图、很长的列表、难读的表格，甚至用 Unicode 字符去模拟颜色。

这不是审美问题，是带宽问题。模型理解了复杂结构，但输出介质不够宽，最后只能压成字符游戏。

但这里有个陷阱：不能把这件事写成“HTML 替代 Markdown”。

更稳的判断是，Markdown、YAML、JSON、代码和数据库记录，仍然适合做 source of truth，也就是事实源。它们负责可追溯、可版本控制、可被机器稳定解析。HTML 更适合做 rendered artifact，也就是渲染出来给人读、给人操作、给人决策的界面。

这两层不能混在一起。

比如一个 PR 解说页面，可以用 HTML 渲染 diff、模块图、风险标签和注释。但真正进入仓库的，仍然是代码 diff 和 review 记录。

一个 feature flag 编辑器，可以用 HTML 做表单、依赖警告和 copy diff。但真正进入系统的，仍然是配置变更。

一个 prompt 调参器，可以用 HTML 做实时预览和 token 计数。但真正复用的，仍然是 prompt 模板和变量。

所以 HTML 的位置不是档案柜，而是工作台。

[转场]

Thariq 原文里最有意思的部分，是双向交互。

他不是只说 HTML 可读。他说，可以让 Claude 做滑块、旋钮、拖拽卡片、实时预览、导出按钮。更关键的是，可以让界面把人类操作后的结果复制成 JSON、prompt、diff，再贴回 Claude Code。

这就不是传统文档了，而是一个临时生成的小工具。

原文里的例子很典型。比如，把 30 个 Linear tickets 做成 Now、Next、Later、Cut 四列拖拽卡片。比如，做一个 feature flag 表单编辑器，按模块分组、显示依赖、提醒前置开关。再比如，做一个 prompt 调参器，左边编辑模板，右边用三个样例实时渲染，顺便显示字符数和 token 数。

这些东西如果做成正式产品，会显得过度设计。如果写成 Markdown，又很难操作。HTML artifact 刚好卡在中间：它是一次性的，但足够可用；它不是产品，但能把人类判断变成结构化反馈。

这可能是 Agent UI 的一个新方向。很多界面不会预先存在于产品里，而是在任务现场临时生成。用完之后，它的价值不是长期存在，而是把人类从一大段抽象文本里拉回循环。

为什么是 Claude Code 特别适合这件事？

原因不是模型本身，而是上下文入口。

Claude Code 能读文件系统、代码目录、Git 历史，也能通过 MCP 接 Slack、Linear、浏览器上下文。它不是凭空写一个漂亮页面，而是能从真实工作材料里抽出结构，再渲染成页面。

Thariq 提到，他写这篇文章时，让 Claude Code 读自己的代码文件夹，找出所有生成过的 HTML 文件，分组归类，再生成带图示的 HTML 文件。文章里的图，就是这个过程的结果。

这说明，HTML artifact 的价值不只是展示。它来自 Agent 对上下文的摄入和重组。上下文越真实，HTML 越不像网页模板，越像任务现场的临时控制台。

[转场]

当然，HTML 的工程账并不轻。

Thariq 自己也承认，HTML 可能比 Markdown 多花 2 到 4 倍时间。HTML diff 也很难审，噪声比 Markdown 大得多。

这两个缺点决定了，HTML 不适合作为所有东西的最终源文件。尤其在企业里，长期维护、多人协作、进仓库、接受审计的东西，仍然需要 Markdown、YAML、JSON、代码这类稳定格式。

更合理的企业模式，是三层分离。

第一层，source of truth。用 Markdown、YAML、JSON、代码、数据库记录保存可追溯事实。

第二层，rendered interface。用 HTML 把复杂信息变成可读、可点、可比较的界面。

第三层，audit trail。把人类在界面里的操作导出成 diff、JSON、prompt 或决策记录，再进入系统。

这比“HTML 干掉 Markdown”更无聊，但更接近真实工作。

这对 AI 从业者意味着什么？

第一，以后写 Agent 任务时，别只写“输出 Markdown”。更好的写法是定义 artifact 的用途：谁读，读完要做什么，需要哪些交互，最后导出成什么。

第二，团队内部的 Agent 交付物应该分 source 和 view。source 用 spec lock、JSON、Markdown、代码保持可追溯；view 用 HTML、SVG、图文页降低理解成本。

第三，Agent 生成 UI 会先从内部工具爆发。PR 说明、事故报告、研究摘要、方案比选、配置编辑、prompt 调参，这些场景都不需要长期产品化，却经常需要临时界面。

第四，审查机制要跟上。HTML 页面看起来更像成品，容易让人降低警惕。但事实、引用、参数变更和导出 diff，仍然要回到可验证源。界面提升阅读率，不等于提升真实性。

所以，这期的结论是：Markdown 没死。它会更多退回后台，成为源、草稿、日志和契约。HTML 会走到前台，成为短命、具体、可操作的 Agent 工作界面。

好的 Agent 输出格式，不是让人更少参与，而是让人更容易参与。这才是 Thariq 这篇文章真正锋利的地方。
