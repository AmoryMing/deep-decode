嗨，欢迎来到 AI 前沿拆解。今天这期，我们讲 Cat Wu 在 Lenny 播客里的访谈。她是 Anthropic Claude Code 和 Cowork 的产品负责人之一，访谈里最有价值的地方，不是讲 Anthropic 有多快，而是讲清楚了一个更底层的变化：AI 原生产品团队，已经不再按传统路线图工作了。

过去，产品经理的核心能力，是把昂贵的工程资源组织起来。你要写 PRD，要排季度 roadmap，要对齐跨团队依赖，要尽量避免做错。因为代码贵，错一次很贵，所以组织会自然长出很多计划和协调流程。

但 Cat Wu 说，Anthropic 很多功能的周期，已经从六个月压到一个月，一周，甚至一天。这不是简单的“大家更拼”。真正的变化是，AI 把工程实现变便宜了。实现变便宜以后，最贵的东西就变成了判断：什么值得做，什么时候发出去，失败以后怎么回收。

所以这篇文章里，我用了一个词，叫“发射台产品学”。传统 PM 像是在维护路线图，Anthropic 的 PM 更像是在维护发射台。发射台不是没有流程，而是把流程压缩到离发布最近的位置。

Cat 提到三个动作。第一，目标必须非常清楚。谁是用户，问题是什么，哪些场景必须开箱即用，哪些路径不做。第二，很多功能以 Research Preview 的方式发布。它告诉用户，这是早期功能，可能会变，也可能不会长期支持。这样团队就不需要把每次上线都当成永久承诺。第三，他们有一个常驻 launch room。工程师觉得功能 ready 之后，文档、PMM、DevRel 可以很快接上，隔天就能把说明和公告补齐。

这里的关键不是“少流程”，而是“流程短”。很多团队说自己敏捷，但每次发布都要重新找人、重新解释、重新对齐。那其实只是小号瀑布。真正的发射台，是把重复协作动作固定下来，让一个真实想法能很快碰到用户。

访谈里第二个很硬的点，是 Cat 讲的 “right amount of AGI-pilled”。她说，为超级 AGI 模型设计产品很容易，难的是为当前模型榨出最大能力。

这句话非常重要。很多 AI 产品会犯两种错误。第一种是剂量太低，把 AI 当传统功能增强，继续套旧流程。第二种是剂量太高，直接为幻想中的全能模型做一个文本框，期待模型自己理解所有上下文、补齐所有工具、完成所有验证。

Anthropic 的产品策略夹在中间。当前模型已经很强，可以做复杂任务，但仍然会漏测 UI、误解约束、忘记长任务边界。所以产品要做的事，是把用户带到模型最擅长的黄金路径上，同时替模型补上它现在还不稳定的部分。

Claude Code 的 todo list 就是一个例子。早期模型做大规模重构时，会说要改二十个调用点，结果改了五个就停。团队给它加了待办列表，相当于给模型一个外部手指，让它逐项记住任务。后来模型变强，已经会自然使用待办列表，这个功能就从强制补丁变成了用户可见的进度提示。

这背后有个原则：AI 产品里的很多功能都有保质期。今天的按钮、提示、工作流，可能只是为了补今天模型的缺口。模型一升级，原来的补丁就可能变成负担。产品经理难的不是多写功能，而是判断哪些脚手架还在帮模型，哪些已经开始挡路。

第三个变化，是 eval。Cat 说，一个 PM 不一定要写几百个评测，十个高质量 eval 就能帮团队量化目标、看清进度、暴露缺口。

这其实是在重新定义 PM 的工作。传统产品里，PM 写需求，工程实现，QA 验收。AI 产品里，这三件事开始挤在一起。因为模型行为不是确定性的，如果需求不能转成可重复检查的任务，团队就很难判断一次模型升级到底让产品变好了还是变坏了。

比如，“模型要更懂前端验证”这句话太抽象。一个好 eval 会更具体：给它一个仓库，一个前端修改任务，一个明确成功标准。改完以后必须打开 UI 验证页面真实可用，不能只跑测试。这样团队才知道失败发生在哪里，是系统提示误导了模型，还是子代理漏做验证，还是主代理没有检查子代理的工作。

Cat 还提到一个很有意思的方法：问模型为什么做错。模型跳过 UI 验证时，不只是记录失败，而是让它反思为什么这样决策。这个动作不像传统用户访谈，更像产品经理在调试一个半透明的工作流。你不是只看结果，而是在找哪里误导了它。

所以 eval 不是 QA 的附属品。它正在变成产品定义本身。谁能定义好完成标准，谁就在定义产品。

第四个点，是角色边界变软。Cat 说，PM 会做一些工程，工程师会做 PM，设计师也在 PM 化和落代码。Anthropic 的 Claude Code 团队，更偏向招聘有产品品味的工程师，很多 PM 也有工程背景。

这不等于 PM 没了。更准确地说，职位边界在变软，但稀缺能力在变硬。

以前，一个 PM 可以靠协调复杂组织、管理路线图、写清楚需求获得价值。现在，如果工程师一周能做出多个版本，而 PM 还停在等大家对齐后再开工，PM 就会变成节奏瓶颈。相反，一个能看懂模型能力、判断用户任务优先级、写出好 eval、推动发布闭环的人，不管头衔叫 PM、工程师还是设计师，都会更值钱。

Cat 对产品品味的解释也很具体。Anthropic 会收到大量 GitHub issue，用户想要所有东西。问题不是有没有需求，而是哪些值得做，用什么形态做，做出来后是否让用户更接近核心任务。代码越便宜，选择越贵。

这也是为什么她说 “Just do things”。这不是鸡血口号，而是一种组织协议。只要你理解约束，能解释判断，就先把该做的事做掉。AI 原生团队里，很多价值来自不端着地补缺口。

最后，Cat 也没有把快速发布包装成无成本神话。她说，Anthropic 牺牲了一部分产品一致性。

这很诚实。一个团队每天都有新功能，每周都在试新形态，产品套件里一定会出现重叠路径。对老用户，这是探索空间。对新用户，这可能就是迷宫。用户不知道完成一个任务，到底该用 Claude Code CLI，Desktop，Web，Mobile，还是 Cowork。

所以 onboarding 重新变得重要。早期团队可能希望产品足够直觉，不需要教程。但当功能和最佳实践增长太快，不做 onboarding 反而会伤害用户。产品复杂度不会因为理念消失，它只会转移到用户身上。

这对所有 AI 产品团队都是提醒。快速发布不是终点。真正的竞争力，是让用户在快速变化里仍然有稳定感。核心任务要稳定，外围形态可以试验。任务成功率要稳定，交互形态可以重写。使命和团队原则要稳定，产品表面可以高速迭代。

这期给从业者的落地结论很直接。

如果你是 PM，不要只练提示词技巧。更值得练的是三件事：把模糊目标写成可执行成功标准，把失败样本转成 eval，把一个想法压缩到一周内能给真实用户试的形态。

如果你是工程师，不要只把 AI 当代码加速器。工程师正在获得更多产品权力，因为你离实现成本、模型能力和真实反馈更近。但权力会暴露品味。能从用户反馈里判断该做什么，比能让模型多写几千行代码更稀缺。

如果你在管理 AI 产品团队，别照搬 Anthropic 的表层动作。少流程不是没有流程，Research Preview 不是随便发，launch room 不是拉个群。真正要复制的是底层机制：目标清楚、发射摩擦低、反馈回路短、评估可重复、失败能回收。

还有 Cat 对自动化的提醒，也值得记住：百分之九十五的自动化，不算自动化。因为最后百分之五，会让人不敢信任系统。真正有价值的内部 AI 工具，不是一次性 demo，而是每天都用，能稳定完成重复任务，并且越用越贴近你偏好的工作流。

今天就讲到这里。我的判断是，Cat Wu 这次访谈不是在讲 Anthropic 有多快，而是在讲 AI 产品组织的新默认值：路线图还会存在，但它不再是中心。中心变成了一个能快速发射、快速反馈、快速回收的产品系统。
