今天聊一条 Shiv Sakhuja 在 X 上发的长推。题目叫 Skill Graphs 2.0，但我们今天聊的不是这个名字，是它底下的一件事——为什么 Claude Code 用户半年来私下抱怨的那个问题，今天终于有人把它说清楚了。

[转场]

问题是这样的。最近大家都在玩 skill graph，就是把每个技能写成 markdown 文件，让技能之间像 Obsidian 笔记一样互相链接。听起来很优雅。一个写邮件的技能依赖一个图形设计的技能，再依赖一个品牌色规范的技能。看起来是图，跑起来也是图。但实际跑下来，链路一深就塌。Agent 在某一层就走丢了，忘了调下层，或者绕进了循环依赖。

[转场]

Shiv 的解释是这样的。每一层技能调用，本质都是一次大模型的自主决策——它要读上下文、判断该不该调下一层、调哪个、传什么参数。这些决策不是确定性函数，是概率事件。哪怕单层九成的正确率，五层下来也只剩五成九。这是数学问题，不是工程问题。把每层写得再显式，从八成提到九成五，也只是把指数衰减的曲线压平一点点，挡不住。

[转场]

所以他给的解法不是更聪明的图算法，而是分层。把所有技能切成三层。最底是 atoms，原子，单一动作，比如发邮件、查邮箱、跑 tavily 搜索。中间是 molecules，分子，用显式工作流串起 2 到 10 个原子。最上是 compounds，化合物，编排多个分子，是真正交给 agent 自主判断的层。他公司内部分别叫 capabilities、composites、playbooks。

[转场]

听起来像化学比喻，但其实这套切法在工程史上反复出现过。写代码是函数、模块、服务。组织设计是 IC、经理、CTO。计算机底层是指令、子程序、进程。三层不是 Shiv 的发明，是人脑能稳定 hold 住的最大抽象数。心理学叫它 working memory chunking。再加一层，driver 自己就糊了。

[转场]

这里面最有意思的一句话是这样的：你坐在驾驶位干嘛，你的车是全自动驾驶。意思是，如果你在用 agent 跑原子级的活儿，等于一个 CTO 在亲自修 bug，浪费的是你的脑 RAM。脑 RAM 是稀缺资源，不是模型算力。一个人最多并行盯五个 agent，所以每个 agent 都应该跑最高抽象的任务，而不是反过来。

[转场]

Shiv 给了个公式，五个 compound 并行等于五百个原子任务的产能。但这个公式有水分。它假设每一层都能稳定十倍展开，而当下的大模型在 compound 层做不到。实测三到五倍是常态，所以一百倍是上限不是常态。更要命的是测试成本。每加一层抽象，测试笛卡尔积同步膨胀。Shiv 自己也承认，测试时间是这套架构最大的挑战。

[转场]

回到我们自己的内容工厂。我对着 Shiv 这套切法审了一遍。capabilities 层是空的——发邮件脚本、转图脚本、tavily 搜索这些原子动作，全部散在 molecule 内部，没法独立测试。composites 层最稳，distribute、polish、visual、podcast 这几个 pipeline 都是合格的分子。playbooks 层只有一个 deep-decode，但它编排了六个分子，已经逼近 Shiv 给的八到十上限，所以也是工厂里失败率最高的那个。

[转场]

推论很清晰。下一步不是再加 compound，而是把藏起来的 atom 显式化，让 deep-decode 在每个判断点暴露给我一个明确的 yes 或 no，而不是自动一路跑到底。skill graph 2.0 不是给 agent 减负，是给人重新分配工作。把做事留给原子和分子，把决定做什么留给化合物和驾驶它的人。

[转场]

如果你也在攒自己的 Claude Code skill 库，今天能立刻做的三件事是：第一，把每个 skill 标上层级，看看你的原子层是不是空的。第二，砍依赖深度，超过三层就反着设计，把深层的原子拉到顶层显式调用。第三，承认 compound 层需要人，别把全自动当目标，把人在判断点介入当目标。代码越便宜，选择越贵。skill 越多，分层越贵。
