title: 你一写MANDATORY就塌了
---

## 一行字判定失控

当你开始往 prompt 里塞 `MANDATORY`、`DO NOT SKIP`、`YOU MUST`，说明这条路已经被榨干了。原作者 Brian 的判断很狠：你不是在调试，你在做语言学研究——想用更强的措辞让一个非确定性系统变得确定。问题是大写字母没有更大写。一个 agent 跑 20 次有 3 次跳过验证，你加一行全大写指令把跳过率从 15% 压到 8%，松口气上线。这不是修复,是自我安慰。

## 散文没有合约

整篇文章立在一个类比上:「想象一种语言,statement 只是给运行时的建议,function 可能幻觉返回值,你根本没法 reason about it。」这就是 agent 现状:每个 prompt 步骤是一条建议性 statement,每个 LLM 调用是一个可能幻觉的 function。3 步跑 1 次能用,30 步跑 1000 次必崩。散文不能 unit test,加一句话可能让另外八句失效。处方一句话:把逻辑从散文搬进运行时。

## 不是新观点但该被听见

Brian 没发明什么,他把分散在工程师 Slack、推文、PR 评论里的共识压成 350 字。Harness 这个概念早有:模型贡献约 60% 的产品质量,Harness 贡献 40%——但那 40% 是可工程化、可积累、可竞争的。模型能力在头部三家趋同,Harness 才是还能拉开差距的地方。最干净的活证据:某编程 agent 的 system prompt 只有约 20 个词,复杂度全压在 50 万行执行层代码里。

## 反对派也有活

公平起见,反对的声音得听完。最强一种:把控制流写死在代码里等于给 agent 套脚镣,你用 2026 年此刻对任务的理解,去固化一个 2027 年才跑的系统,模型升级了你的 if-else 还在。第二种更钝:客服分流、长文写作、研究综述,你写不出确定性 scaffold,LLM 就是核心决策器。所以这不是银弹。适用场景是:步骤可枚举、每步可验证、错误代价不可接受。混着用才对。

## 三层防护只能选一种

文章最后一段是干货。会无声失败的系统需要主动错误检测。如果 agent 不能在出错时大声叫,你只剩三个选项:一是人在环里,每步确认,可靠但 agent 的意义没了;二是跑完穷尽审计,慢、贵、漏检;三是接受不验证,出事再说,代价不可控。这清单被刻意设计成不舒服。Brian 没列「加段 prompt 让它自检」——那不是验证,是请被告自证清白。没有第四种舒服解法。

## 风向变了

这篇 350 字便签在 HN 炸出 153 条评论,信号是行业注意力正从「调教模型」转向「包装模型」。grep 你的 codebase,搜 `MANDATORY`、`DO NOT`、`ALWAYS`、`NEVER`,每个命中都是候选:这段逻辑能不能用代码表达?多数时候答案是「能,但我懒」。2024 年的明星是会写 prompt 的人,2026 年的明星会是会写 harness 的人。三家头部都在告诉你:模型这层没什么可争的了,争的是写代码那层。
