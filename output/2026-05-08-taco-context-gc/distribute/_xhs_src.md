---
title: 终端Agent的窗口里44%是垃圾
---

## 窗口大没用,装的是垃圾

让一个跑在 shell 里的 Agent 解 TerminalBench 任务,跑到第 30 步,它已经看不到自己最初要干什么。窗口给到 128K 也照样塞满。TerminalBench 2.0 实测:raw prompt 里 24.6%–44.1% 的内容是低价值冗余。瓶颈不是"窗口不够大",是"垃圾比例太高"。这两件事的解法完全不同。TACO 论文给的判断很直接:上下文要有 GC,窗口越长越值钱,留给垃圾就越亏。

## 一条命令吐一万字符

终端 Agent 的体质特殊。每发一条命令就拿到一段不可预测的 stdout/stderr。论文里的极端例子:一次 apt-get install 输出 10071 字符,99% 是"Unpacking package-X..."的重复行,真正决定下一步动作的只有最后那行 success/fail。但 Agent 不知道哪行关键,10071 字符全进了下一轮 prompt。原文一句:"保留原始观测能留下有用的环境反馈,但也导致上下文饱和与高昂 token 成本。"token 成本按步数二次方往上爬。

## 让规则自己长出来

固定规则走不通:同一段 gcc 输出在 build 任务里是关键参数,在调依赖任务里就是噪声。训专门模型也走不通:终端环境分布几乎无穷。TACO 选第三条路——用 LLM 自己写压缩规则,按任务动态进化,全程不训模型,挂在现有 Agent 外面就能用。冷启动只放 6 条种子规则,覆盖 git、pip、apt、compiler 等高输出命令。每条规则是可读、可审计、可手改的 JSON,不是黑盒。

## 收敛靠一个硬信号

任务跑起来,遇到压不住的高输出命令就触发 LLM 写新规则;如果 Agent 反复请求"show me the full output",系统判定规则过激,触发回滚。任务结束,被验证有效的规则带着 confidence 写回全局池,下个任务直接复用。收敛判据很硬:Top-30 规则跨任务 Retention 超过 90%,连续多轮基本不变,就认为压缩前沿稳定。永远在"学习"的系统才是玄学,能停下来才是工程。

## 省钱和涨分同时拿到

跨六个 200B+ 模型在 TerminalBench 上跑,TACO 同时拿到"token 更省"和"准确率更高"。每步 token 平均降约 10%。跨 benchmark 迁移更说明问题:DevEval 上 token 砍掉 27%,准确率反而涨 1.6 个点。一般效率优化里要么砸钱换准确率,要么省钱掉准确率,能同时往上只有一个原因:砍掉的那部分本来就在拖准确率。垃圾不是中性的,它在主动伤害模型判断。

## 单纯压缩不是目的

消融实验把这点说狠了。DeepSeek-V3.2 + TB 2.0 上:完整 TACO 是 42.7% 准确率、12.2% token reduction;去掉任务内演化后 token 降到 30.7% reduction,降得最猛,但准确率掉到 38.9%,三个配置里最低。结论很清楚:单纯压缩不是目的,"在不杀掉关键信号的前提下压缩"才是。压得越狠不等于越好,关键看砍的是不是真垃圾。

## 内存管理开始分层

把 TACO 放进上下文压缩家族:Prompt Caching 压的是计算成本不是长度;Auto-Compaction(Claude Code 用的)是不可逆的全局摘要,丢掉的细节找不回来;ACON 效果好但要训练、要权重、迁移成本高。TACO 占了之前空着的位置——不训练,又能动态适配场景。Agent 工程的"内存管理"开始分层:KV cache 像 L1,prompt cache 像 L2,TACO 这种规则 GC 是 heap GC,auto-compaction 才是 OOM 时的 swap。

## 给从业者的一个问题

评估终端 Agent 类产品时,问一个具体问题:"在第 50 步时,前 49 步的命令输出还在 prompt 里吗,还是已经被压过?压的策略是什么?"这个答案直接决定同一产品在 5 步任务和 50 步任务上的成本差能拉开 10 倍以上。把上下文窗口当内存,不是数据库。10 万 token 是工作集,不是归档区。Auto-compaction 是应急方案,不该是日常策略。
