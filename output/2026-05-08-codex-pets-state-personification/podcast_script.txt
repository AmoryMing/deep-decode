嗨，欢迎来到 AI 前沿拆解。

今天讲一个看起来很轻的小功能：Codex 的桌宠。

如果只看表面，这就是一个会动的小伴侣。你可以在 Codex App 的设置里选一个 pet，也可以输入 /pet 唤醒它，或者用命令面板里的 Wake Pet 和 Tuck Away Pet 控制它出现和收起。

但这个功能真正有意思的地方，不在“可爱”，而在它解决了 Agent 产品里的一个老问题：当一个 AI 在后台持续工作时，用户怎么知道它还在跑、是否卡住、是否正在等自己、是否已经到了 review 阶段。

传统软件用 spinner、进度条、通知来处理状态。但 Agent 不一样。它不是下载一个文件，也不是提交一个表单。它可能跑测试、改代码、查文档、等权限、等你 review。这个过程时间更长，状态更多，也更不确定。

所以 Codex 的桌宠，本质上不是宠物，是一层低噪的状态界面。

OpenAI 官方文档里有一句关键描述：这个浮动 overlay 会在你使用其他 App 时，保留 Codex 的活跃工作状态。它会显示当前线程，并反映 Codex 是 running、waiting for input，还是 ready for review。

这就把定位讲清楚了。

它不是为了让你跟一个小角色聊天。它是把 Codex 的后台工作，从主窗口里拎出来，放到你的工作环境边缘。

你不用一直盯着 Codex 窗口，也不用等每一步都弹通知。你只要扫一眼，就知道现在是它在干活，还是轮到你接手。

这就是我想说的“状态拟人化”：把抽象状态变成一个有形象、有动作、有短提示的存在。

注意，这里的重点不是人格化。人格化会让系统看起来像另一个人。状态拟人化更窄，它只是在帮你理解工作流。

[转场]

这里可以和 Claude Code 之前泄露源码里的 buddy 系统做一个对照。

Claude buddy 走的是另一条路线。它更像一个真正的电子伙伴：有名字，有性格，有物种，有稀有度。源码里把它拆成两层，一层是“灵魂”，也就是名字和性格；另一层是“骨架”，也就是物种、稀有度、眼睛、帽子这些外观属性。

更细的是，骨架不是直接存本地配置，而是由用户 ID 加盐之后确定性生成。这样同一个用户每次看到的都是同一只，但你不能靠改配置把自己改成稀有款。

这是一套身份系统。它想制造的是“这是我的那一只”。

Codex pets 目前公开出来的路线不同。它没有强调稀有度、扭蛋、反作弊，也没有把重点放在孵化一个伙伴上。它的命令是 wake 和 tuck away。也就是唤醒一层状态，或者把它收起来。

这个语义差异很重要。Claude buddy 更像“伙伴”；Codex pets 更像“工作状态灯”。

[转场]

Claude buddy 源码里还有一个特别值得借鉴的设计：角色分离。

它在 prompt 里明确告诉主模型：你不是这只 companion，它是一个 separate watcher。用户叫 companion 名字的时候，气泡会回答，主模型要让开。

这听起来像小细节，其实是桌宠类功能能不能成立的边界。

如果主 Agent 和桌宠混成一个角色，用户会听到两个声音。一个在解释任务，一个在装可爱。很快就会吵。

好的设计应该是：主 Agent 解决问题，桌宠表达状态。主 Agent 负责行动，桌宠负责让用户感到系统还在场。

从这个角度看，Codex pets 最合理的架构应该是旁路观察者。它不参与主任务，不改变决策，只订阅线程状态，把 running、waiting、review 这些状态翻译成用户能扫到的提示。

为什么它需要这么多入口？

官方文档列了三个入口：设置页、/pet、命令面板。

这不是重复，而是三种场景。

设置页负责配置：选哪个 pet，刷新自定义 pet。

/pet 负责在当前对话里快速唤醒，不打断工作流。

命令面板负责跨界面控制。当你已经在 Codex App 里，不想离开当前上下文，Cmd+K 或 Ctrl+K 是最短路径。

这说明 Codex 把桌宠当成一层可折叠状态界面。你需要它时，它在；你嫌它挡时，它退下。

更有意思的是自定义 pet。官方文档给的路径是安装 hatch-pet skill，重新加载 skills，然后让 skill 创建一个受近期项目启发的新 pet。

这一步超过了换皮肤。它把界面资产接进了技能系统。也就是说，未来 Agent 的界面可能和工具一样，是可编排、可生成、可个性化的。

[转场]

当然，现在公开信息还很少，有几个问题不能跳过。

第一，状态映射是否够细。官方现在提到 running、waiting for input、ready for review。但真实开发任务里，还有测试失败、权限请求、网络阻塞、分支冲突、CI 等待。桌宠能不能表达这些，决定它是装饰，还是仪表盘。

第二，自定义 pet 到底能改什么。如果 hatch-pet 只能换外观，它就是主题系统。如果还能改状态文案、提醒粒度、项目语境，那它就是个人化 Agent UX 的入口。

第三，隐私边界。overlay 会在你使用其他 App 时显示活跃线程和进度提示。企业环境里，线程名和任务提示可能有敏感信息。一个常驻浮窗必须足够克制，否则低噪状态层会变成低空泄露风险。

第四，用户会不会把桌宠当成真正的主体。桌宠越像一个角色，用户越容易把成败归因到它身上。产品需要拿捏：给 Codex 一个身体，不等于给它一个不受控的人格。

[转场]

对做 AI 产品的人来说，Codex pets 的信号很明确。

Agent UX 的下一层竞争，不是再加一个聊天框，而是处理长期运行的不确定性。

如果你的产品里有长任务、后台执行、等待用户确认、等待 review，那你需要一种更轻的状态表达。它不一定是桌宠，也可以是小浮窗、小状态条、项目级仪表盘。但它必须让用户知道：现在是谁的回合。

如果你做企业 AI 产品，重点不是可爱，而是可扫视。审批流、报表生成、知识库同步、数据清洗，都有同一个问题：用户不想每五分钟点开看一次，也不想被每一步通知打断。

如果你做平台，custom pet 更值得看。Codex 把 pet 接进 skill 系统，说明未来 Agent 不只是任务可编排，界面也会被编排。

[转场]

这里还可以提炼出三个产品原则。

第一个原则，状态要比人格更优先。很多 AI 产品一谈拟人化，就急着给角色加语气、名字、头像。其实对工作型产品来说，用户最先需要的不是一个会闲聊的角色，而是一个可靠的状态解释器。它要告诉用户，现在有没有进展，卡在哪里，下一步要不要你出手。

第二个原则，常驻不等于高频打扰。桌宠类界面最容易犯的错，是把“活着感”理解成一直动、一直说话、一直刷存在感。Claude buddy 的源码反而给了一个好范例：空闲时大部分时间静止，偶尔眨眼；只有被触发时才兴奋。Codex pets 如果要长期留下来，也必须克制。

第三个原则，个性化应该服务工作流。自定义 pet 不应该只是在换外观。真正有价值的自定义，是不同项目、不同状态、不同风险等级，有不同的表达方式。比如生产环境任务更克制，个人 side project 可以更轻松；等待 review 时强调轮到你，跑测试时只保留低噪提示。

这三个原则放在一起，桌宠就不再是一个 UI 小彩蛋，而是 Agent 产品的“在场协议”。

最后收一下。

过去软件状态是机器语言：spinner、badge、进度条。

现在 Agent 的状态开始变成人类能感知的存在。

Codex pets 是一个很小的入口，但它指向的问题很大：当 AI 不再只在窗口里回答，而是在后台持续工作，产品需要一种新的在场语法。
