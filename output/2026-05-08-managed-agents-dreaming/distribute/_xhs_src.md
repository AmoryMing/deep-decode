title: agent学会做梦，完成率飙6倍
---

## 第三件套叫"梦"

去年厂商把 agent 的脑和手拆开卖，这个月补上了第三件，名字叫梦。机制其实直白：让 agent 在没事干时回看自己之前几百次会话，找出反复栽跟头的地方，然后改自己的系统提示词。人类睡觉时大脑做的事，被翻译成了一条 API。dreaming 这个词第一眼像营销，翻到那条完成率数字才发现不是。

## 反应式agent的天花板

过去两年 agent 的模式是固定的：收请求、推理、调工具、输出、会话结束，然后从零开始。问题不在某次做得好不好，在它做不好同一类任务里那个反复出现的坑。客户名字写错纠正一次,下个会话又错。每个团队都在给系统提示词打补丁。我见过一个 600 行的 system prompt，几乎每行都对应过去某次客诉。这是反应式脚手架的最终归宿:补丁博物馆。

## 完成率提升约六倍

把 session 当语料,喂给一个专门的复盘 agent,它只读自己不执行任务,输出系统提示更新建议。法律 AI 跑通后报告完成率提升约六倍。得拆穿一点:这是厂商自报数字,不是独立测评。但即使打对折,这个量级也超过模型版本升级能给的。模型一年里实际任务收益大概 20%-40%,这套机制在长任务上一下 300%。差距不是模型做的,是脚手架做的。

## 把验收变成API

agent 自己不知道自己干完了没。Outcomes 让开发者写一份成功标准(规则或 rubric),系统启动独立 grader 在另一个上下文窗口里评估产出,不达标就拿着反馈再来一次。数据:总成功率 +10pp,docx +8.4%,pptx +10.1%。结构化产出物收益最大,这类任务本来就有客观验收标准。本质是把产品经理的验收清单 API 化:能定义需求的人,变得比管开发的人值钱。

## 裁判和运动员要隔开

为什么非要独立的 grader?因为同一个 agent 自评会作弊。这不是阴谋论,是实测过的偏差——LLM 评估自己输出时倾向给高分,行内叫 self-preference bias(自评偏好偏差)。厂商干脆把裁判和运动员物理隔开,独立上下文独立评分。这条结论的意义比功能本身大:agent 自检要靠架构,不是靠在提示词里写一句"请客观评价你自己"。

## 数百个子agent并行

第三件套是多 agent 编排:主 agent 拆任务,子 agent 并行干,共享文件系统但不共享上下文。某流媒体公司用主 agent 把上千份构建日志切片,分发给数百个子 agent 并行扫异常。"数百个"这个数字比"多 agent 协作"有用得多,它告诉你适合的场景:批量、可拆分、子任务独立、结果可汇总。日志分析、批量代码审查、对账全是。当前限制一级委派,子 agent 不能再调 agent。

## 锁点又埋深了一层

也得说坏处。这是厂商把锁点往深埋了一层。session 格式锁过一次,现在 dreaming 的提示更新格式、Outcomes 的 rubric DSL、子 agent 的编排协议,每一个都是新的标准位。开发者一旦在上面建立 evaluation 基础设施,迁移成本就不只是切 API,是重做整套质量保障流程。云厂商的 lock-in 也不是从虚拟机开始的,是从权限和监控开始的。同样的剧本。

## 时间成了评测新轴

最值得记的判断:harness 的职能从管运行扩到了管成长。同一个用了 dreaming 的 agent,第一周和第十周的表现可能差出三倍——你测哪一周?传统的"任务成功率"是单点测试,时间维度成了 evaluation 的新轴,几乎所有 benchmark 都还没跟上。对从业者:rubric 比代码更值钱,能讲清"什么叫做完了"的人最稀缺。组里没专门做 eval 的,赶紧补一个。
