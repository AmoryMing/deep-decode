# Playbook v1.1

> 目的：把云端的"how"提炼成本地可重现的 SOP + 写作判断。这份文件是 voice.md 的**操作侧补充**，不替代 voice.md。
>
> **样本量**：22 个 vault bundle（#1-#22）已 ingest，覆盖 7 种 mode（event-decode / meta-decode / paper-decode / talk-decode / hot-history / source-code-decode / practice / manual / entity-decode 候选）。**18 种钩子方式**已观察。
>
> **证据数约定**：
> - ⚡ 候选（1 篇出现，待验证）
> - ✅ 双篇验证（2 篇同模式，可执行但仍可推翻）
> - 🔒 多篇固化（3+ 篇，稳定规则）
>
> **维护规则**：每吃完一个 bundle，回头看每条 ⚡ 是否升 ✅、每条 ✅ 是否升 🔒、是否有新规则浮现、是否有规则被推翻。证据回溯标注到具体文件具体段落，便于审阅。
>
> **置信度（截至 v1.1）**：
> - 🔒 固化：5 phase 工作流 / 7 段思考骨架（事件型）/ 10 项 polish 自查清单 / 7 步散文级润色标尺 / 信号 taxonomy / 8 章模板 / 概念命名密度 / 数据归属语 / 用市场行为做证据 / 反向声音署名 / 不暴露加工 / 钩子反向判定 / 钩子多样化（18 种实证分布）
> - ✅ 双篇验证：hot-history 子模式 / meta-decode 子模式 / source-code-decode 系列模式 / 抓官方一个词当解剖刀的写法
> - ⚡ 候选（待更多样本）：实体拆解骨架（仅 #3 一例未成稿）/ 配图位置规则 / talk-decode 拆传播现象 / 系列内部钩子多样性

## A 部分：操作性 SOP（从素材到成稿）

### A.1 工作流总览（5 phase）

✅ 双篇验证。云端的 decode 文章不是一稿成型，是 5 个 phase 串起来的：

```
Phase 0  调研 (research)        → phase0_research.md / phase0_sources.json
Phase 1  骨架 (skeleton)        → phase1_skeleton.md
Phase 2  信号 (signals)         → phase2_signals.json
Phase 3a 草稿 (draft)            → draft_v1.md
Phase 3b 事实核 (factcheck)     → factcheck.json + draft_v2.md
Phase 3c 润色 (polish)           → polish_report.json + 终稿
```

【证据：#1 完整保留 phase0/1/2/factcheck/polish_report 五份；#2 phase0_research.md（366 行）+ 终稿 article.md，phase1/2/factcheck/polish 未持久化但成稿质量等价（说明可省，但 phase0 + 自查不可省）】

**意味着什么**：本地写作时不能跳过 phase 0/1。"打开就写"是云端从不做的事。

### A.2 Phase 0：调研 SOP

✅ 双篇验证：

#### A.2.1 必备字段（每条事实都要齐）

| 字段 | 说明 | 例 |
|---|---|---|
| **claim**（事实本体） | 数字/事件/引言 | "Figma 股价当天跌 7%" |
| **source URL** | 精确到原文 | gizmodo.com/.../immediately-nosedives-... |
| **status** | 是否已交叉验证 | Accurate / Accurate-with-attribution / 待补 |
| **judgment**（独立段） | 这条数据"意味着什么" | "资本市场和人事动作同时给答案" |

【证据：#1 factcheck.json 22 条 claim 都附 sources 数组；#2 phase0_research.md 每条事实下方都跟"判断"段】

#### A.2.2 交叉验证最低标准

🔒 候选规则（也写入 voice.md 的"必备"）：**每条核心事实最少 3 个独立信源**。理想结构：1 官方 + 1 第三方技术媒体 + 1 一线开发者/被影响方。

【证据：#1 phase0_sources.json 所有 primary_events 都列 ≥3 个 source；#2 phase0_research.md 末尾"交叉验证"段落给 5 个 URL】

#### A.2.3 原话引用四件套

✅：每条引言必须四件齐——

```
> "原文英文" —— 说话人 / 来源（带 URL）
> 中文：翻译
```

【证据：#1 §引用 6 条；#2 phase0_research.md 全部引言都按此格式】

#### A.2.4 "信源待补"必写

✅：phase0 末尾**显式列出未能确认/未深挖的项**，给下游写作风险预警。

【证据：#2 phase0_research.md "信源待补"段列 4 项；#1 factcheck.json `unresolved_errors: []` 即使为空也写】

#### A.2.5 多线索叙事（meta-decode 专用）

⚡ 候选（暂只在 #2 见完整形态）：当一篇文章合并 2+ 个事件，phase0 应按"线"组织（线 1 / 线 2 / 线 3...），每线独立的时间线 + 关键事实 + 原话 + 判断 + 交叉验证。

【证据：#2 phase0_research.md 4 条线（GPT-5.5 / Anthropic 反应 / 开发者口碑 / Codex App 更新）】

### A.3 Phase 1：骨架 SOP（两种骨架按拆解类型选择）

云端有两种 phase1 骨架，按拆解对象选——

| 拆解类型 | 适用对象 | 骨架 | 篇幅 |
|---|---|---|---|
| **事件拆解（event/article decode）** | 单篇文章 / 一个声明 / 一个事件窗口期 | 7 段思考骨架（A.3.1） | ~5000 字 |
| **实体拆解（entity decode / 横纵分析法）** | 产品 / 公司 / 技术概念 / 人物 | 横纵 5+4+1 项（A.3.2） | 10000-30000 字 |

判别：
- 主语是"X 文章 / X 声明 / X 这一周" → 事件拆解
- 主语是"X 产品 / X 公司 / X 协议 / X 人物" → 实体拆解

#### A.3.1 事件拆解骨架（7 段）

✅：phase1_skeleton.md 必有这 7 段，缺一不可——

| # | 段名 | 关键问题 |
|---|---|---|
| 1 | **核心论点（一句话）** | 全文如果只能保留一句话，是哪句？ |
| 2 | **隐含假设** | 作者/行业默认但没明说的几条假设？ |
| 3 | **关键证据（最强 2-3 个）** | 拎出能独立支撑论点的证据，多了反而稀释 |
| 4 | **盲区** | 作者刻意没提 / 官方外交辞令 / 数据漂亮但没说什么衡量 |
| 5 | **读者画像** | 至少 2-3 个身份，每个身份写"对你意味着什么" |
| 6 | **内容结构（章节规划）** | 章节顺序 + 每章一句话主旨 + 配图位置 |
| 7 | **可视化规划** | 配图清单（编号 / 章节 / 概念 / 形式建议） |

【证据：#1 phase1_skeleton.md 严格按这 7 段】

**反向思考的两个段最有价值**：
- 隐含假设——把约定俗成的等号拆掉（例 #1：「设计 ≈ 用 Figma 做界面」这个约等号本身就是被拆的对象）
- 盲区——把官方话术翻译成市场行为（例 #1：「complement Canva not replace」← Figma 7% 跌幅）

#### A.3.2 实体拆解骨架（横纵 5+4+1 项）

⚡ 候选（vault 内仅 #3 entity-claude-design 一份证据，且 bundle 未完成成稿，无法验证骨架→成稿的转化质量）：

来源 `knowledge/horizontal-vertical-analysis-prompt.md`（数字生命卡兹克方法论），核心公式：**纵向追时间深度，横向追同期广度，最终交汇出判断**。

**纵向 5 项（沿时间轴追深度）**：
1. 起源追溯——技术/理念/需求来源 + 核心推动者 + 当时行业环境
2. 诞生节点——首次发布/成立/提出时间，最初形态和定位
3. 演进历程——关键节点时间线（不是流水账，要因果关系）
4. 决策逻辑——还原"为什么选 A 不选 B"+ 当时约束
5. 叙事弧线规划——起承转合（铺垫 / 蓄力 / 明牌 / 爆发 / 转折）

**横向 4 项（同期赛道切面）**：
6. 竞品场景判断——A（无直接竞品）/ B（1-2 个）/ C（3+ 充分）三选一
7. 竞品逐一——每个 1500+ 字独立展开（路线/目标用户/优势/短板/定价/真实口碑）
8. 生态位分析——版图位置 + 填补空白 + 正面竞争对象 + 护城河
9. 趋势判断——12-24 月走向 + 机会面 + 风险面

**交汇 1 项**：
10. 横纵交汇——纵向脉络 + 横向格局 → 综合判断 + 原创概念命名 + actionable insight（按读者身份分组）+ 可视化规划

**适用对象**：产品 / 公司 / 技术概念 / 人物。

**重要风险**：
- vault 中 #3（2026-04-22 entity-claude-design）启动但未完成成稿——它后来在 2026-04-24 转换为 meta-decode 形态（#1 ai-design-three-layer）发布。说明实体拆解骨架在长篇深度（10000-30000 字）和 meta-decode 之间存在选择困难，**云端最终选了更短的合并解读形态**。这是一个尚未解开的悬念
- 篇幅 10000-30000 字是企媒 decode 的 6 倍量级，对配图、节奏、读者耐心都是新挑战

【证据：#3 phase1_skeleton.md 严格按横纵 5+4+1；knowledge/horizontal-vertical-analysis-prompt.md 是方法论原始定义】

### A.4 Phase 2：信号 SOP

✅：phase2_signals.json 列 5-8 个核心信号，每个信号必备——

```json
{
  "type": "信号类型（见下表）",
  "source": "信源名称",
  "url": "原文 URL",
  "role": "在文章里扮演什么角色（佐证/反面/对照/补充）",
  "key_point": "一句话精髓"
}
```

#### 信号类型 taxonomy（合 #1 和 #2 共出现的）

| type | 说明 | 在文章里的位置 |
|---|---|---|
| `market` | 股价 / 资本反应 / 财报 | 「数据/资本佐证」段 |
| `official_partner` | 合作伙伴/客户站台 | 「生态选择」段 |
| `competitor_context` | 竞品同期动作 | 「赛道挤满」段 |
| `data_benchmark` | 产业渗透率 / 行业数据 | 「不是孤例」段 |
| `technical_detail` | 一手技术细节（架构/参数） | 论点放大段 |
| `designer_voice` / `developer_voice` | 一线使用者反向声音 | 「内部反向声音」段 |
| `timeline` | 事件先后排列 | 钩子段 / 时间压缩段 |

【证据：#1 phase2_signals.json 含 6 条，type 跨 5 种；#2 phase0 内嵌的"线 3 开发者实测口碑"四个子线索是 designer/developer_voice 的密集形态】

### A.6 Phase 3b：Factcheck SOP

✅：

#### A.6.1 逐条事实核对

每个 claim 单独条目，给出——

| 字段 | 例 |
|---|---|
| `claim` | "gpt-image-2 一次最多出 10 张图" |
| `status` | `Accurate` / `Accurate-with-attribution` / `Accurate (已修正)` / `待补` |
| `sources` | 数组，至少 1 个 URL |
| `note` | 必要时说明（"为 X 个人观察，已归属"/"原文合并 A 和 B 易误读") |

【证据：#1 factcheck.json 22 条 claim 全部按此格式】

#### A.6.2 corrections_applied 必写

修改过的位置必须显式记录：

```json
{
  "location": "§三 会思考的像素",
  "before": "一次生成最多 10 张图并保持角色一致",
  "after": "一次最多可以出 10 张图，其中最多 8 张能保持人物和物体的一致性",
  "reason": "原文合并了'10 张出图上限'和'8 张一致性上限'两条不同数据，易误读"
}
```

【证据：#1 factcheck.json corrections_applied 1 条】

#### A.6.3 主观语言审计（subjective_language_audit）

✅：每篇必扫——

- **最高级声明**："最强 / 最大 / 最 X" 的所有出现，每条说明是否归属（"Anthropic 官方宣传，非独立声明"等）
- **情感倾向词**：检查"震惊/炸裂/细思极恐/不可思议"——必须为零
- **价值排序**：检查"必须/推荐/应该"——必须为零（描述性陈述代替）

【证据：#1 polish_report 和 factcheck 都跑这一项】

#### A.6.4 unresolved_errors 字段

✅：即使为空也要写（`[]`），是显式承诺"我已扫过"。

### A.7 Phase 3c：Polish SOP（10 项自查清单）

✅ 双篇验证：终稿前必跑这 10 项。**不是逐段 subagent，是整体扫描**——大文章并行 polish 边际收益递减且有 over-polish 风险。

| # | 项 | 检查点 |
|---|---|---|
| 1 | **钩子开头** | 反向判定：**不像 PR 稿 / 新闻摘要 / "今天聊聊"**，且**不与最近 3 篇用同一招**。具体方法不限，详见 C.0 |
| 2 | **AI 签名词** | 全文搜：「让我们」「综上所述」「值得注意的是」「接下来看」「首先...其次...」——必须为零 |
| 3 | **反复"不是X而是Y"** | 全文计数，>2 次就稀释 |
| 4 | **原创命名嵌入叙事** | 概念命名直接出现在论述里，不用「本文提出 X 概念」元叙述 |
| 5 | **双受众/多受众** | 至少 2 个身份的"对你意味着什么"段落 |
| 6 | **推理链完整** | A → B → C → 推论，不跳步 |
| 7 | **外部信号数 ≥ 3** | 不同信源数清点，<3 就薄 |
| 8 | **盲区/反面论证段** | 官方刻意没说的 / 内部反向声音，至少 1 段 |
| 9 | **落回具体** | 结尾不抽象升华，落到具体场景/读者动作 |
| 10 | **企媒适配子项** | 无祈使句 / 无价值排序 / 不贩卖焦虑 / 不暴露加工 |

【证据：#1 polish_report.json 完整跑这 10 项；#2 终稿全部满足这 10 项（反向验证）】

#### Polish mode 选择

- **light-polish**（整体自查）：原稿质量 OK，跑一遍清单 → 修个别小处 → 完。**默认选项**
- **heavy-polish**（逐段 subagent）：仅当原稿明显粗糙才用

【证据：#1 polish_report `mode: "light-polish"` 并解释"20+ 段并行 evaluator 边际收益递减"】

### A.7b Phase 3c 散文级润色：7 步标尺

🔒 **直接固化**（来源：`knowledge/polish-7steps.md`，2026-04-21 v1.0，作者明确为 deep-decode Phase 3.5 评估标尺）。

A.7 是**结构级**自查（钩子 / 信号数 / 盲区 / 落地段...），下面 7 步是**散文级**润色，颗粒度到段落和字词——

| Step | 维度 | 检查 |
|---|---|---|
| **1** | 术语精度 | 听起来对但所指不同的词 / 中英混用是否有惯用译名 |
| **2** | 指代与事实 | 数词代词回上下文核对 / 代码与正文描述咬合 |
| **3** | 翻译腔排毒 | 否定阶梯（不是X不是Y是Z）/ 被动滥用 / 长定语从句 / 介词框架 |
| **4** | 以实代虚 | "东西/事情/问题/部分/方面"等万能缩水词换具体名词 |
| **5** | 节奏与动词 | 列举骈散结合（前短后长）/ 中性动词换带画面分量态度的（"超过"→"抵得上"） |
| **6** | 留白克制 | 删所有作者替读者做的反应（"你看多震撼""令人意外"） |
| **6.5** | **加工过程不可见**（2026-04-21 新增，**优先级高于 Step 7**） | 暴露 vault / CLAUDE.md / wiki / schema / SKILL.md / "本文/作者/我们" / dogfood / "用 LLM 帮助写作" → 整段删除或重构为领域判断 |
| **7** | 意象贯穿 + 声音保留 | 立了什么核心意象（呼吸/流水/皮肉骨/秤）后续比喻必须收拢；个人化表达保留（"转圈的小玩意儿"不改"加载指示器"） |

#### 原则

> **改错不改味，炼字不炼魂。**

#### 关键边界

- **段落级处理**：每次只处理一段，不整篇塞
- **1 轮 hard stop**：Generator 按 Evaluator 报告改完一次就定稿，不二次评估（防过度修饰修到走味）
- **Step 6.5 优先级最高**：作者个人化表达如果暴露加工过程，必须删；"转圈的小玩意儿"这类不涉加工过程的口语化才适用 Step 7 保留

#### 输出格式（Evaluator subagent 必须严格产出）

每段一份 JSON：
```json
{
  "paragraph_id": "p_003",
  "original": "原段落",
  "revised": "改后段落",
  "insights": [{"original": "...", "revised": "...", "rule_cited": "Step 3", "why": "..."}],
  "overall_diagnosis": "本段核心问题集中在 Step 3 + Step 4..."
}
```

【证据：knowledge/polish-7steps.md（2026-04-21 v1.0）；#11 memex-llm-wiki polish_report.json 显式引用 Step 3/4/5 改写 4 处 + Step 6.5 整节删除"《写这篇文章的过程本身就在吃自己的狗粮》"】

#### 与 A.7（10 项结构自查）的关系

- **A.7 是宏观**：整篇结构 / 章节 / 信号数 / 盲区段是否存在
- **A.7b 是微观**：段落 / 字词 / 节奏 / 意象 / 翻译腔
- **执行顺序**：先跑 A.7（全篇扫一遍），再跑 A.7b（按段落润色）

#### 与 voice.md 三大忌的关系

| voice.md 三大忌 | polish-7steps 对应 |
|---|---|
| 原创概念自命不凡 | Step 6 留白克制（删"本文原创"） |
| 技法堆砌显廉价 | Step 5 节奏（每段不超过 1-2 个技法）+ Step 7 意象贯穿 |
| 翻译腔 | Step 3 翻译腔排毒（4 类直译结构） |
| **第四忌（不暴露加工）** | **Step 6.5 加工过程不可见** |

## B 部分：文章结构模板（操作性）

### B.1 标准 8 章 decode 模板

✅ 双篇验证。两篇都是这个骨架——

| 章节 | 作用 | 长度提示 |
|---|---|---|

#### B.2.1 hot-history 子模式（2 篇验证）

✅ 双篇验证。骨架——

1. **钩子**：权威人物顺嘴提了一句历史 + 「话只说到这里就停了」 → 自己接上加码（#12 skills-frames）；或 当代爆款 + 大时间跨度（#11 「一条 gist 把 80 年拉直」）
2. **历史源头精读**：找原文最强一段引言精读
3. **失败的继承人队列**：列出 N 代试图实现同一愿景但失败的项目
4. **失败原因的命名**：把共同失败原因抽出一个原创命名（#11「维护税」/ #12「知识获取瓶颈」）
5. **当代解法**：解释为什么这一次不一样
6. **反对意见段**：「税没消失，只是换了形式」式的反向声音
7. **对从业者意味着什么**：落地段

**核心修辞：死因即解药**——老想法死于 X，今天的新工具正好解决 X。

【证据：#11 / #12 严格按上述骨架】

## C 部分：知识性判断（写作原则）

> 这一部分**不重复 voice.md 已有的规则**。只列两篇验证出的、voice.md 未明确的、或在 voice.md 中模糊的判断。

### C.0 钩子开头的灵活性原则（🔒 用户反馈固化 2026-04-25）

**反面规则比正面规则更重要**。把钩子分类列清单（"时间压缩 / 单一数据 / 矛盾陈述"）本身就是八股的源头——读者一眼能识别模板。

#### 判定标准（反向）

钩子合格的判据不是"用了哪种招"，是同时满足三点反向条件：

1. **不像 PR 稿 / 新闻摘要 / "今天聊聊 X"**——这是底线
2. **不与最近 3 篇用同一招**——重复使用同一种钩子（即便那种钩子本身不烂）也会被一眼看穿
3. **读完第一段想不想往下看**——这是终极标尺，不是清单勾选

#### 可用的方向（不是清单，是空间）

时间压缩 / 单一数据 / 矛盾陈述 / 一句意外引言 / 反常识断言 / 故事开头 / 反问 / 当下场景描写 / 把术语翻译成大白话当首句 / 不在任何已知类别里的新写法——**只要不闷、和上一篇不一样**。

可以混搭（一个钩子里同时有时间压缩+引言）也可以无明显套路。

#### 自审动作

- 写完钩子读出声，**自问"这像不像我上一篇的开头"**——像，重写
- 自问"这像不像 PR 稿/新闻稿"——像，重写
- 自问"如果不告诉读者后面有什么，这一段能不能让人想点开"——不能，重写

#### 为什么不放更多招进 polish 自查清单

如果在第 1 项写"必须用这 5 种钩子之一"，下一篇我可能在 5 种里挑一种 → 5 种轮一遍 → 5 篇之后又是八股，只是周期长了。**清单化思维本身就是八股的根源**，不是清单不够长的问题。

【证据：用户反馈 2026-04-25。注意 #1 (5 天 3 件事) + #2 (60 小时窗口) 两篇都用时间压缩——已经是固化早期信号】

### C.1 概念命名密度（✅）

- **每篇 5-8 个原创命名**，集中在"本期关键词"段。
- **命名嵌入叙事**：第一次出现时直接写在论述里（如「这层分工变化，用一个词概括就是：**设计三段分层**」），不用元叙述（「本文将提出一个新概念叫 X」）。
- **命名要可独立传播**：四到六字 + 自带画面（"设计三段分层""分叉领先""意图到像素短链路""锯齿形前沿"），不要术语堆砌（"AI-augmented design pipeline architecture"）。

【证据：#1 §关键词列 7 个；#2 §术语列 6 个；polish_report 第 4 项专项检查】

### C.2 数据归属语必须显式（✅）

- 官方声明用"声称 / 据 X 报道 / 官方表述为"
- 个人观察用"X 的判断是 / X 给的数字是"
- 第三方数据用"据 X 数据"
- **不允许悬空数字**（"成功率 33%"必须写"无结构化规划时 ~33%（Fanny 个人观察）"）

【证据：#1 factcheck.json `Accurate-with-attribution` 标 2 条；#2 文中所有 benchmark 数字都标了来源】

### C.3 用市场行为而非声明做证据（✅）

- 官方话术 = 外交辞令（不可信）
- 资本动作 / 人事变动 / 法务行为 / 产品状态标签 = 真信号

例：
- #1：Anthropic 说"complement Canva not replace"（官话）↔ Figma 7% / 35% / Krieger 辞董事（市场）
- #2：Anthropic 默不作声（CEO 在白宫处理政治）↔ 三次 dumb-down 同日披露（被动公关）

【证据：#1 §五"两个不会被说破的盲区"；#2 §三 + §六 同模式】

### C.4 Research Preview / 工程标签要主动解读（⚡）

任何官方加在产品上的"标签"本身在传话——Research Preview = 产品没准备好但能力天花板高。要主动把标签翻译给读者。

【证据：#1 §五专门解读 Research Preview】

### C.5 反向声音必须有名有姓（✅）

每篇至少引一个"内部反向声音"（设计师 Fanny / Simon Willison / XDA / 客户 BNY Mellon / NVIDIA 员工），不是"业内人士"这种匿名。**反向声音的可信度建立在身份具体性上**。

【证据：#1 §四 Fanny；#2 §五 XDA + Willison + BNY Mellon CIO】

### C.6 配图位置规则（⚡）

- 每篇 4-6 张配图（不是越多越好）
- 配图嵌入对应章节，**不集中在文末**
- 类型分布：1 封面 + 1 概念分层图（§一 论点段）+ 1 对比图（§二/§三）+ 1 反向/压缩图（§四）+ 1 四象限/落地图（§六）

### C.7 不暴露加工过程（✅）

- 不写"本文将拆解 / 本文提出 / 我们认为"
